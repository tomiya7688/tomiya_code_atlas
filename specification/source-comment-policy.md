# Tomiya Code Atlas ソースコメント規約

この文書は、Tomiya Code Atlas のソースコードとテストコードに付けるコメントの規範を定めます。

コメントの目的は、機械解析を容易にすることではありません。**人がコードを読んだときに、責務・意図・前提・入出力・失敗条件を短時間で理解できるようにすること**が第一目的です。

JSON-like Comment Outs を使う場合は、次の仕様を参照します。

- https://github.com/tomiya7688/Json-like-comment-outs
- 日本語版 `docs/jp/SPECIFICATION.md` を正本とする

このプロジェクト固有の読みやすさ規則は、本書を優先します。

## Required（必須）

### 1. コメントは理解を速くするために書く

コメントは、コードを日本語へ逐語訳するために書いてはいけません。

優先して説明する内容:

- その宣言が何を担当するか
- なぜその処理が必要か
- 入力が何を意味するか
- 何を返すか
- 外部状態を変更する場合、何が変わるか
- 呼び出し側が知る必要のある失敗条件
- 実装だけでは読み取りにくい制約や前提

次のようなコメントは避けます。

- 関数名を言い換えただけの説明
- コードを上から読み上げただけの処理一覧
- 型や構文を見れば明らかな説明
- 項目を埋めるためだけの文章
- 機械解析しやすくするためだけの不自然な文章

**コメントを読んでも理解が速くならない場合、そのコメントは追加しないか書き直します。**

### 2. 日本語を基本とする

コメント本文と説明用の項目名は日本語を基本とします。

コード上の識別子、製品名、規格名、ライブラリ名などの固有名詞はそのまま使用できます。

そのまま使用する例:

- Python
- Go
- C#
- GDScript
- Mermaid
- PlantUML
- Roslyn
- JavaParser
- 実際のクラス名、関数名、引数名

日本語で書く例:

- Semantic Key → 意味上の項目
- Function / Method → 関数 / メソッド
- Field → フィールド
- Return → 戻り値
- Action → 処理
- Responsibility → 責務
- Renderer → レンダラー
- Backend → バックエンド
- self-hosting → 自己適用
- fixture → テスト用入力
- golden test → 期待値比較テスト

固有名詞でもコード理解に不要な英単語を増やさないでください。

### 3. JSON-like Comment Outs はカンマありで統一する

元仕様ではカンマは任意ですが、Tomiya Code Atlas が生成・自己適用する JSON-like Comment Outs は、項目境界を目で追いやすくするため**カンマあり**で統一します。

例:

```text
{
  責務: [
    LoadConfig: 設定ファイルを読み込み、アプリケーションで利用できる設定データへ変換する,
  ],
  処理: [
    1: 指定されたパスを確認する,
    2: 設定ファイルを読み込む,
    3: 読み込んだ内容を設定データへ変換する,
  ],
  引数: [
    path: 読み込む設定ファイルのパス,
  ],
  戻り値: [
    config: 読み込んだ設定データ,
  ],
}
```

厳密な JSON 互換性より、ソースコード上で項目の境界が読みやすいことを優先します。

### 4. 宣言レベルと実装内部を分ける

JSON-like Comment Outs は、主に次の宣言レベルへ使います。

- クラス
- 関数
- メソッド
- 言語上それらに相当する主要な宣言

関数内部の条件分岐、処理単位、ローカル変数などは、必要に応じて通常コメントを使います。

実装内部まで機械的に JSON-like 形式へ変換してはいけません。

### 5. 宣言とコメントを一致させる

JSON-like Comment Outs を使う場合:

- 責務には対象の宣言名を含めます
- 引数の名前は実装上の引数名と一致させます
- フィールドの名前は実装上のフィールド名と一致させます
- 実装変更で意味が変わった場合、コメントも同じ変更で更新します
- 存在しない引数、戻り値、処理をコメントへ書いてはいけません

## Required（必須）: テストコード

テストコードも、人が保守・レビューするソースコードです。テストだからコメント不要とは扱いません。

ただし、全テスト関数へ同じ形式の説明を機械的に付けることも禁止します。

### コメントが必要なテスト

次のいずれかに該当する場合、テスト名だけでは不足する意図をコメントまたは宣言レベルの構造化コメントで説明します。

- 過去の不具合を再現するテスト
- 非自明な境界条件を確認するテスト
- 特殊な入力やfixtureを使うテスト
- 期待値の理由がコードだけでは分かりにくいテスト
- 複数機能の相互作用を確認するテスト
- 実装上の制約・互換性を固定するテスト
- 外部backend、配布物、環境差を確認するテスト
- 将来「なぜこのテストが必要なのか」が失われやすいテスト

最低限、次が読み取れるようにします。

- 何を保証するテストか
- どの条件を再現しているか
- なぜその期待値になるか

### テスト用入力・fixture

テスト用入力や期待値データには、必要に応じて次を説明します。

- この入力が代表している言語機能・境界条件
- 意図的に壊している箇所
- 順序、空白、改行、パスなどを固定している理由
- 期待値比較で重要な差

### テスト用helper

複数テストから使う非自明なhelper、builder、mock、fake、fixture生成関数は、通常のプロダクションコードと同じ基準で責務・入出力を説明します。

### コメントが不要なテスト

テスト名と短い本体だけで意図・前提・期待値が明白な場合、冗長なコメントを追加しません。

例:

```python
def test_empty_input_returns_empty_result():
    assert analyze("") == []
```

このようなテストへ「空入力で空結果になることを確認する」とだけ書き足しても理解は速くならないため、不要です。

## Recommended（推奨）

- 「何をしているか」より「なぜそうするか」を優先して書きます
- コメント量ではなく理解速度を品質基準にします
- 既存コメントに有用な背景がある場合、形式変更で削除しません
- 長い説明が必要なら、ソースへ巨大コメントを置かず該当仕様へ参照を残します
- 自動生成したコメントは人がレビューし、意味のない文章を残しません

## レビュー時の確認

コメントを含む変更では次を確認します。

- 実装とコメントが一致している
- コメントがコードの逐語訳になっていない
- 固有名詞以外に不要な英語が増えていない
- JSON-like形式の区切りが読みやすい
- テストの意図・再現条件・期待値理由が必要な箇所で説明されている
- コメントがない方が読みやすい箇所へ無理に追加していない

コメントの量が多いことを品質とはみなしません。
