# AST／意味解析バックエンドの適合fixture

Issue #131では、バックエンド固有のASTやsymbolオブジェクトを言語アダプターの外へ出さずに、parser／意味解析バックエンドを比較するためのバージョン付きfixtureを定義しています。

## 契約

fixtureは `tests/fixtures/backend_conformance/` にあります。

- `manifest.json` は6言語の主fixtureと、それぞれが含む能力プローブを示します。
- `expected_common_ir_v1.json` は言語に依存しない意味解析の期待値です。
- 各言語のソースファイルは、言語仕様が許す範囲で同じ基本構造を表します。

共通する基本構造:

```text
BaseWorker
  ^
  |
Worker
  + run(item)
      -> helper(item)
      -> helper(item)
  + helper(item)
  + async_probe(item)
  + nested_probe(item)
```

各fixtureには少なくとも1つのimport／依存関係も含めます。ジェネリック、async、入れ子スコープは、言語ごとに表現方法が異なるため能力プローブです。たとえばGDScriptはユーザー定義ジェネリッククラスではなく型付きコンテナーを持ちます。

## 期待値から意図的に除外するもの

期待値ではparserの実装詳細ではなくCommon IRの意味を比較します。そのためソース行位置、インデント、AST node名、Roslynのsyntax kind、tree-sitter node type、Clang cursor kind、token ID、バックエンド固有の診断オブジェクトは含めません。

バックエンドはより豊富な情報を内部で保持して構いませんが、Analyzer、Generator、Evaluator、Rendererが参照する前にLanguage Adapterで正規化します。

## 評価フロー

```text
fixture source
  -> 候補parser／意味解析backend
  -> Language Adapter
  -> ModuleIR
  -> 意味情報の射影
  -> expected_common_ir_v1.json
```

言語ごとに最適なparserは異なります。Pythonで実装されていることだけを理由にバックエンドを優先しません。

## CIでの利用

`tests/test_backend_conformance_fixture.py` は通常のCI実行ごとにfixture schemaを検証し、現在のPythonプロジェクトアダプターで期待する意味情報の部分集合を確認します。言語別の評価Issue #132〜#137ではこのfixtureを再利用し、未対応の能力を明示します。正規化した事実を推測で補ってはいけません。

将来Common IRにジェネリック、asyncの意味、symbol解決の項目を追加するときは、v1の期待値を黙って変更せずfixture契約をバージョンアップします。

## シリアライズされたCommon IRのconformance（Go移行）

上記の意味subset fixtureとは別に、`serialized_common_ir_v1.json` はPython adapterが出力するCommon IRとcall graphをgoldenとして固定し、JSON形状とrenderer非依存の論理出力を検証します。診断配列は実出力のまま空で保持し、同じfixture内の `diagnostic_example` で正規化diagnosticの位置形式を示します。これは言語間の意味subsetを広げるものではなく、Goを含む移植先が共有データを読み取り、同じ論理結果を比較できるためのwire-level契約です。

- `schema_version` はCommon IR payloadの版で、現在は文字列 `"1"` です。parser backend envelopeの `contract_version` とは別の版です。
- Go側の受動modelとpayload codecは `go/internal/commonir/` に置き、fixture検証とparser helperで同じ型を使います。言語固有AST型は `backends/go/` のhelper内に留めます。
- 必須領域は `common_ir.language`、`entities`、`imports`、`diagnostics`、`diagnostic_example` と `logical_output.call_graph` です。entityは `kind`、`name`、1始まりの `line` と `end_line` を持ち、診断の `line` は省略可能ですが指定時は1始まりです。`end_line` は対象範囲に含みます。
- 省略可能な追加fieldは読み手が無視します。必須field欠落、型違い、未対応のschema versionは、対象pathを示すエラーにします。互換性のない意味変更や必須fieldの削除は新しいschema versionを作り、既存v1 fixtureを上書きしません。
- v1の受動entityでは、言語共通の`type_name`、`parameter_types`、`return_type`を任意fieldとして使えます。`property`や`field`も`kind`で表し、型とsource locationを保ちます。parser固有nodeやsymbol型はwireへ出しません。
- IRの配列順はproducerが出す順序を保持します。特にentityはsource順、parameter/base/decoratorは意味上の順、`call_sequence` は出現順と重複を保持します。論理call graphのnodesとedgesは集合として扱い、fixtureではnodesを名前順、edgesをcaller・callee・call_type順に正規化し、重複を除きます。renderer固有の文字列はfixtureに入れません。
- `helper_protocol_cases_v1.json` はGo helperとC# helperが共有して実行するrequest/responseケースです。envelopeの `contract_version` / `request_id` とIRの `schema_version`、言語、最低限の正規化entity/import/diagnostic配列を確認します。各helperは言語固有のAST型ではなくCommon IRまたは正規化errorだけをstdoutへ返します。

### Fixtureを更新する

1. `Src/analyzers/ir.py`、Parser Backend Contract、対象helperの出力を確認し、変更が意味上互換かschema変更かを判断します。
2. 互換な任意fieldの追加ならserialized fixtureへ追加し、未知fieldを無視するGo conformance testを維持します。必須field、型、意味、正規化規則を変える場合は新しい `serialized_common_ir_vN.json` とprotocol fixtureを追加し、Go runnerと各CI helper smokeを同時に更新します。
3. `serialized_common_ir_v1.json` の期待値は言語非依存のCommon IRと論理出力に限ります。診断文面や位置を含め、確認したsource事実だけを記録し、parser固有名やrenderer syntaxを入れません。
4. `go test ./...`、`tests/test_go_helper.py`、C# backend smoke、および変更に関係するPython fixture testを実行します。過去versionの互換性を壊す変更では、旧fixtureを残した検証も必要です。
