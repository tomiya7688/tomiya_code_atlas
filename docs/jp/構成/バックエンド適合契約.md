# AST／意味解析バックエンドの適合fixture

Issue #131では、バックエンド固有のASTやsymbolオブジェクトを言語アダプターの外へ出さずに、parser／意味解析バックエンドを比較するためのバージョン付きfixtureを定義しています。

## 契約

fixtureは `tests/fixtures/backend_conformance/` にあります。

- `manifest.json` は6言語の主fixtureと、それぞれが含む能力プローブを示します。
- `expected_common_ir_v1.json` は言語に依存しない意味解析の期待値です。
- 各言語のソースファイルは、言語仕様が許す範囲で同じ基本構造を表します。

共通する基本構造:

```text
BaseWorker
  ^
  |
Worker
  + run(item)
      -> helper(item)
      -> helper(item)
  + helper(item)
  + async_probe(item)
  + nested_probe(item)
```

各fixtureには少なくとも1つのimport／依存関係も含めます。ジェネリック、async、入れ子スコープは、言語ごとに表現方法が異なるため能力プローブです。たとえばGDScriptはユーザー定義ジェネリッククラスではなく型付きコンテナーを持ちます。

## 期待値から意図的に除外するもの

期待値ではparserの実装詳細ではなくCommon IRの意味を比較します。そのためソース行位置、インデント、AST node名、Roslynのsyntax kind、tree-sitter node type、Clang cursor kind、token ID、バックエンド固有の診断オブジェクトは含めません。

バックエンドはより豊富な情報を内部で保持して構いませんが、Analyzer、Generator、Evaluator、Rendererが参照する前にLanguage Adapterで正規化します。

## 評価フロー

```text
fixture source
  -> 候補parser／意味解析backend
  -> Language Adapter
  -> ModuleIR
  -> 意味情報の射影
  -> expected_common_ir_v1.json
```

言語ごとに最適なparserは異なります。Pythonで実装されていることだけを理由にバックエンドを優先しません。

## CIでの利用

`tests/test_backend_conformance_fixture.py` は通常のCI実行ごとにfixture schemaを検証し、現在のPythonプロジェクトアダプターで期待する意味情報の部分集合を確認します。言語別の評価Issue #132〜#137ではこのfixtureを再利用し、未対応の能力を明示します。正規化した事実を推測で補ってはいけません。

将来Common IRにジェネリック、asyncの意味、symbol解決の項目を追加するときは、v1の期待値を黙って変更せずfixture契約をバージョンアップします。
