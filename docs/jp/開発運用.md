# 開発運用

Tomiya Code AtlasではGitHub Issueを作業台帳とし、原則として「1 Issue ≒ 1 PR」で進めます。

## 標準の作業手順

### 作業開始時にリモートの最新状態を確認する

Issueの実装に入る前に、まずremoteの最新状態を確認します。

```powershell
git status --short --branch
git fetch --prune origin
git rev-list --left-right --count main...origin/main
git pull --ff-only origin main
```

fast-forwardできない場合は、local commitを確認してから `git merge --no-edit origin/main` で取り込みます。conflictは解決後にtestで確認し、force pushでremoteの履歴を上書きしません。

### Windowsビルドの検証

ルートの `build_exe.bat` はGo版Windows EXEとGo/Python/C#/C++/Java parser helperを作り、`run_dist.bat` はGo CLIを起動します。Python版は移行中の参照・test用sourceとして残し、アプリ本体として配布しません。setup、source版の起動、parser helperと全体検証を行う補助batは `scripts/build/` にまとめています。

- `scripts/build/setup.bat`: Python 3.12を優先し、利用できない場合はPython 3.11以降で `.venv` を作成する。
- `scripts/build/build_go.bat`: `go/` moduleのtestを実行し、Windows用EXEを`.build/dist/`に作成する。
- `scripts/build/build_go_parser_backend.bat`: `backends/go/` helperをtestし、配布先へGo parser EXEを作成する。
- `scripts/build/build_python_backend.bat`: CPython AST helperをruntime同梱のone-dirとしてbuildする。
- `scripts/build/build_csharp_backend.bat`: Roslyn helperを.NET 10 self-contained win-x64 folderとしてbuildし、Roslyn licenseを同梱する。
- `scripts/build/run_source.bat`: source版を起動する。
- `scripts/build/verify.bat`: Go EXE、Python/C# helper、Python source tests、policyを確認する。
- `scripts/dev/pull_request.bat`: この検証後にGitHub PRを作成または更新する。

Go版EXEとhelperのbuildにはGo 1.22以降、Python 3.11以降、.NET 10 SDKが必要です。配布artifactはPython runtimeと.NET runtimeをparser helperに同梱するため、利用者はそれらを別途導入しません。v1.0.0 release workflowは全移行Issue完了まで作成しません。

### IssueからPRまで

```text
Issue
 -> priority + Goal / Required / Acceptance
 -> scripts/dev/prepare_work.bat / scripts/dev/prepare_work.sh
 -> Task Capsule + remote delta + Context Pack
 -> Responsibility / Change Routing
 -> bounded search / structure index
 -> implementation
 -> targeted validation + policy check
 -> compact diff / compact log when useful
 -> scripts/dev/pull_request.bat
 -> CI / review / merge
```

## Issueの選択

- P0: 基盤／阻害する正確性
- P1: 主要な機能
- P2: 拡張／生産性
- P3: 将来／優先度の低い改善

priority labelを正とし、なければtitleの `[P0]`〜`[P3]` prefixを使います。meta／roadmap／umbrella／indexを目的とするIssueは、対応可能な実作業がある場合、自動選択では後回しにします。

Issueには必要に応じてGoal、Required constraints、Acceptance、Priority、Out of Scope／Deferredを記載します。`scripts/dev/next_issue.bat` はその内容を `.codex/next_issue.md` に抽出します。正本は元のIssueです。

## 探索範囲の制御

次の順に読みます。

```text
Task Capsule／metadata
 -> 責務マップ／file role map
 -> 範囲を絞った検索／structure index
 -> 対象source
 -> 対応するtest
 -> 直接の依存先
 -> 必要なときだけ詳細文書
```

Goal、Required、Acceptance、working setが明確になったら広範な探索を止めます。`scripts/dev/context.bat exploration-stop` はこれらを機械的に確認します。成功しても、実装自体が正しいことを意味するものではありません。

## 案内先

- `docs/jp/責務マップ.md`: module／fileの責務
- `specification/architecture-policy.md`: 規範的なRequired / Recommended / Advisory rule
- `docs/jp/現状.md`: 現在の機能と阻害要因
- `docs/jp/機能仕様/`: taskに対応する機能詳細
- `scripts/dev/context.bat role-map`: file roleの機械的な索引
- `scripts/dev/context.bat truth-candidates`: 正本と断定せず、正本候補の場所を表示

大きな文書は無条件に全体を読むのではなく、heading検索（`doc-index`）や範囲を絞ったtext検索から入ります。

## 先に検索し、必要な箇所だけ読む

`scripts/dev/context.bat search` と `path-find` は追加依存なしのfallbackです。`rg`、`fd`、IDE index、ctags、tree-sitterなど、より強いlocal toolが既にあれば利用できます。基本の作業にそれらを必須にしてはいけません。

検索／索引の出力は読むsourceを選ぶために使います。sourceそのものの代わりにはしません。

## ソース構造index

`scripts/dev/context.bat structure-index` は `Src/` と `tools/` のPython symbol／import indexを決定的に出力します。fallbackの案内機能です。将来はCode Atlas自身のCommon IR／call／dependency解析で置換または拡張します。

```text
target symbol -> 直接関係 -> 対応するtest -> 必要な場合だけgraphを深掘り
```

fan-in／fan-out／cycleは影響範囲を探す手掛かりであり、自動的な設計判定ではありません。

## remoteの変更差分を先に確認する

別のAI、chat、developerがremoteを変更した可能性がある場合は `scripts/dev/context.bat remote-delta` を使います。ahead／behind、commit subject、変更file、shortstat、範囲を限定したdiff excerptを確認します。full changeを読むのは現在のtaskと関係する場合に限ります。

`remote-delta --ff` は明示的な指定です。dirty／diverged状態では止まり、fast-forwardだけを実行します。

## Context Pack

`scripts/dev/context.bat context-pack` は現在のTask Capsule、変更file、validation plan、簡潔なdiff、remote状態、探索状態から `.codex/context_pack.md` を作成します。これは一時的な派生contextであり仕様ではありません。過去の内容を積み上げず、必要に応じて作り直します。

## repositoryの規模／context予算

`scripts/dev/context.bat profile` はrepository統計、全体を読む場合の概算token量、file type、長いtext fileを報告します。品質評価ではなく、contextが集中する場所を見つけるために使います。

## 変更とlogを簡潔に調べる

`compact-diff` は変更file、shortstat、commit subjectを返します。handoff／PR summaryではこれを既定にします。実際のreviewや曖昧さの調査にはfull diffも使います。

`compact-log` はerror／warning／failureと範囲を限定した末尾を残します。成功logは通常pass／failだけで要約し、失敗箇所を調べる場合に限り生logを広げます。

## 検証方法の案内

`scripts/dev/context.bat validation-plan` は変更fileに応じた検証を案内します。

- logic: 対象test -> regression -> 基準を確認して必要なら広いtest
- architecture: 対象test + `policy-check`
- GUI: まずheadless動作、見た目がAcceptanceに含まれる場合は画面も目視確認
- packaging: test -> build -> sourceだけで分からない場合はartifact smoke
- 生成物／一括変更: 再現可能な変換／dry-run／代表例確認
- random／時間依存: input／seed／時間上限を固定してstructuredな観察

対象が0件のcheckは根拠になりません。未確認の事項は `Unverified` として報告します。

## 規範ルールの案内

規範の正本は `specification/architecture-policy.md` です。`policy-check` は機械判定できるruleを確認し、確定したerrorとwarning／review signalを分けます。意味上の設計判断には対象を絞ったreviewが必要です。

Required ruleの例外はrule、理由、範囲、軽減策、再確認／削除条件、正本への参照を記録します。

## 情報の責務

- README: 人向けの概要
- AI_CONTEXT: AI向けの短い案内
- 現状: 現在の機能／阻害要因
- 責務マップ: ownership案内
- `docs/jp/`: 日本語の説明／機能設計の正本
- [`docs/en/`](../en/README.md): 日本語正本から作成した英語版
- `specification/`: 規範的なrule
- Issue: 要件／priority／未完了の作業
- source + test: 実装済みの振る舞い
- `.codex/`／生成report・diagram: 派生artifact

同じ詳細な仕様を複数の情報面に重複させないでください。

## コマンド

Windowsでは `scripts/dev/context.bat command`、Linux／macOSでは `./scripts/dev/context.sh command` を使います。

主なcommand:

- discovery: `profile`、`doc-index`、`search`、`path-find`、`role-map`、`truth-candidates`、`structure-index`
- state／change: `remote-delta`、`compact-diff`、`context-pack`
- control: `exploration-stop`、`validation-plan`、`policy-check`、`compact-log`

`scripts/dev/prepare_work.bat` / `prepare_work.sh` は通常の準備手順を実行します。`scripts/dev/next_issue.bat` はpriority順のTask Capsuleを作ります。`scripts/dev/pull_request.bat` は低contextな検証・commit・push・PR作成を行います。

## 採用した方法

このprojectは `ai-context-reducer` とUPD policy practiceから、短いAI入口、Current State、Task Capsule／Context Pack、Search-first／Read-second、範囲を絞った検索／path発見、探索の終了条件、明示したOut of Scope、対応可能Issueのpriority選択、Task／Change Routing、責務マップ、file role／正本索引、Source Structure Index、context profile／予算／hotspot、Remote Delta First、簡潔なdiff／log、Validation／Policy Routing、rule強度／範囲付き例外、deterministic優先の構造解析、生成／雑音データの除外、簡潔なhandoff、明確な情報責務など、有用な方法を採用します。

repository全体を恒常的に解析する巨大frameworkや常時稼働のcall graph cacheは別に持ちません。共通解析が成熟したらCode Atlas自身が、より豊かなstructure indexを提供します。

### UPD Commander Checker

CIは `tools/requirements-upd.txt` からupstream repositoryのmain branchを追従するPython UPD Commander Checkerを導入し、`upd-commander-check .` を実行します。この汎用UI／Process／Data checkは、Tomiya固有の `scripts/dev/context.bat policy-check` を補います。開発用toolであり、runtimeや配布依存には含めません。
