# 責務マップ

実装ファイルを開く前に、このマップで作業範囲を絞ります。各責務は短く保ち、詳細な振る舞いはソース、テスト、機能仕様に記載します。

| 領域 | 責務 | 主な依存・補足 |
|---|---|---|
| `go/cmd/tomiya-code-atlas/` | Go版のCLI起動入口 | Core/Processを呼び出し、解析・入出力の実処理を持たない |
| `go/internal/commonir/` | Go移行用の受動的な共有IR/modelとversioned JSON codec | language-neutralなentity/module/relation/location/diagnosticを定義し、parser固有型と処理調整を持たない |
| `go/internal/analyzers/` | Common IRに対する決定的な共通解析 | 現在はcall graph、package依存、fan-in/out、到達範囲、深さ制限、循環検出を含む。parser固有型とRenderer構文に依存しない |
| `go/internal/conformance/` | Go移行用のCommon IR serialized fixture検証 | 共有modelのcodecでversion、必須JSON shape、source location、logical outputを検査する |
| `backends/go/` | Go標準ライブラリによるparser helper | Go ASTを共有Common IRへ正規化し、UI・保存・分析調整を持たない |
| `Src/languages/go_backend.py` | Go parser helperのContract v1 host adapter | 同梱helperを起動し、Go固有型を漏らさずCommon IRへ変換 |
| `backend-src/csharp/`, `backends/csharp/` | Roslyn C# parser helperと配布物 | Roslynのsyntax tree／semantic factsをCommon IRへ正規化し、self-contained .NET runtimeとlicenseを同梱 |
| `backends/cpp/`, `Src/languages/cpp_backend.py` | Clang C++ translation-unit parser helper | compile_commands.jsonがあればflagを利用し、namespace／record／function／include／diagnosticをCommon IRへ変換。libclangをPyInstaller one-dirへ同梱 |
| `backend-src/java/`, `Src/languages/java_backend.py` | JavaParser Java 26 grammar helper | package／class／interface／record／enum／field／constructor／generic／annotation／methodをCommon IRへ正規化。jlinkで作ったprivate Java runtimeとライセンスを同じ配布物へ同梱 |
| `backends/python/` | CPython標準ASTとTree-sitter GDScript grammarを使うParser Backend Contract v1 helper | Python／GDScriptをCommon IRへ正規化し、PyInstaller one-dir配布物にruntimeとparserライセンスを含める |
| `go/internal/staticdoc/` | Common IRから静的仕様書Markdownを生成 | Python ASTやhostのprocess orchestrationに依存しない |
| `docs/jp/構成/Go共通Analyzer移行対応表.md` | Go共通Analyzer移行のPython parityと移植状況 | Issue #195の対象Analyzer、fixture、意図した差を記録する |
| `app.py`, `scripts/build/run_source.bat` | 移行期間中のPython版起動入口 | Go配布物からは呼び出さず、参照・test用にする。Python配布物はbuildしない |
| `build_exe.bat`, `run_dist.bat`, `scripts/build/` | Windowsアプリとparser helperのビルド・起動・検証 | root入口からGo CLIと言語parser helper／必要runtimeを作る。補助スクリプトはリポジトリroot基準で動かす |
| `.github/workflows/go-exe.yml` | Go版Windows配布物のbuild・smoke・artifact公開 | Go CLIと配布対象のparser helperを検証する |
| `Src/languages/` | 言語別解析とアダプター | 外部parser/ASTの詳細はここで閉じ、共通モデル／IRへ変換する |
| `Src/analyzers/` | 決定的な関係・フロー・グラフ解析 | 共通モデルを使い、Rendererの構文に依存しない |
| `Src/models/` | 受動的な共有データ契約 | 小さくシリアライズしやすく保ち、機能オーケストレーションを持たせない |
| `Src/generators/` | 解析結果から論理出力を生成 | 出力形式の構文を持ち込まない。古い言語依存は移行時の警告候補 |
| `Src/renderers/` | Mermaid / text / 将来形式へのシリアライズ | 言語解析をせず、形式固有の関心事をここへ置く |
| `Src/models/static_specification.py`, `Src/generators/static_specification.py`, `Src/renderers/static_specification_markdown.py`, `Src/process/static_specification_service.py` | Common IRから静的仕様書Markdownを生成 | call relationship解析はProcess serviceが調整し、Python parserの詳細をGenerator／Rendererへ漏らさない |
| `Src/evaluators/` | 設計・コード品質の評価 | 可能な範囲で言語非依存の解析結果を利用する |
| `tools/next_issue.py` | 優先Issueを選択してTask Capsuleを作成 | 決定的に動作し、LLMへ依存しない |
| `tools/create_pr.py` | 検証・要約・push・簡潔なPR作成 | あいまいさや失敗の調査に必要な場合だけ全diffを読む |
| `tools/context_tool.py` | リポジトリ／context索引と簡潔なpolicy・validation補助 | 生成物は索引であり、正本ではない |
| `docs/jp/機能仕様/` | 機能単位の設計と受け入れ条件 | 作業に対応する仕様だけ読む |
| `docs/jp/構成/` | アーキテクチャの説明と対応関係 | 背景と案内を記載し、規範ルールは `specification/` に置く |
| `docs/jp/開発運用.md` | Issue / PR / contextの作業手順 | 安定した運用ルールを記載する |
| `docs/jp/現状.md` | 現在の機能と阻害要因の要約 | 大きな状態変化に応じて更新し、変更履歴にはしない |
| `specification/` | 規範となるRequired / Recommended / Advisoryルール | 例外は対象範囲を明示する |
| `tests/` | 実行可能な振る舞いと互換性の根拠 | テスト名から対象の責務領域が分かるようにする |
| `tests/fixtures/backend_conformance/` | 言語横断の意味subsetとserialized Common IR/helper protocol fixture | semantic projectionとwire-level contractを別fixtureで保つ |
| `tests/fixtures/analyzers/` | Python/Go共通Analyzerの論理出力golden | 各実装が同じ相対import・node・edge・cycle結果を使って検証する |
| `.github/workflows/` | CIの根拠とpackage公開のゲート | 簡潔で決定的な検証を優先する |

## 参照手順

最初に対象領域の行を確認し、必要に応じて次の順に読む。

```text
責務領域
  -> 対応するテスト
  -> 直接の依存先
  -> 必要な場合に限り該当仕様
```

将来関係しそうという理由だけで、すべての領域を読む必要はありません。

## アーキテクチャ上の兆候

責務を一文で説明できなくなったり、新しいモジュールが明らかに無関係な複数の責務を持つ場合は、設計レビューの対象にします。これは自動分割の要件ではなく、狙いを絞ったアーキテクチャ確認を促す兆候です。

## 更新ルール

大きなモジュールの追加・分割・統合、または責務の変更があった場合は、このマップも同じ変更で更新します。個々の補助関数は列挙しません。
